두 파일에 통째로 중복된 것:

- `UpdateCharacterState` 우선순위 사다리 전체
- 상태 플래그 6개, `Awake`의 콜라이더 기반 `BoundaryRadius`/`GroundOffset` 계산
- 구현 인터페이스 6개가 완전히 동일

**영향**
적 콤보를 손보려면 같은 수정을 두 번 해야 한다. 보스/NPC 추가 시 세 번째 복붙이 된다.

**방향**
- `CharacterControllerBase` 추상 클래스로 공통부를 올리고, 차이나는 지점만 `abstract` 훅으로 남긴다.
- `EnemyIntent`라는 딱 맞는 구조체가 이미 있으니, 플레이어도 InputAction 결과를 Intent로 변환해 같은 파이프라인에 태운다.

**진행 결과 (완료)**

- 신설: `Common/Character/CharacterControllerBase.cs`(535줄), `Common/Character/CharacterIntent.cs`(30줄)
- `PlayerController` 529 → 181줄, `EnemyController` 478 → 66줄
- `EnemyIntent` → `CharacterIntent`로 일반화하고 `AttackToStart` 필드 추가.
  적 Brain은 이 값을 비워두고 베이스가 `firstAttackData`로 채우므로, 브레인 2개는 타입 이름만 바뀌었다.
- 플레이어 입력도 Intent 파이프라인으로 통일. InputAction 콜백은 `pendingAttack` / `jumpRequested`를
  걸어두기만 하고, 같은 프레임의 `UpdateIntent()`에서 소비된다.
  → **유일한 의도된 동작 차이**: 한 프레임(약 16ms) 안에 공격키를 두 번 누르면 한 번으로 합쳐진다.
- 파생 클래스가 채우는 훅 5개: `UpdateIntent` / `Uses8DirectionSnap` / `UpdateFacing` /
  `IsMovingForState` / `OnDeath`
- 인스펙터 필드 통합: `enemyLayer` + `targetLayer` → `targetLayer` 하나
  (`[FormerlySerializedAs("enemyLayer")]`로 플레이어의 기존 값 보존)
- `currentHealth`를 `protected`로 선언해 `HealthDebugDisplay`의 리플렉션이 무수정으로 동작
- 검증: Unity Roslyn(`csc`)으로 Assembly-CSharp 전체 컴파일 통과 (에러 0)

**덤으로 잡은 버그 — Impulse 공격 후 Stun 오표시**

돌진(Impulse)은 `movement.ApplyKnockback`을 재사용하므로 그라운드 슬라이드로 구현된다.
그런데 `AdvanceComboOrEnd`가 공격이 끝나는 순간 `selfImpulseActive`를 끄는 반면,
`IsGroundSliding`은 감속이 끝날 때까지 계속 true로 남는다.
→ 그 틈에 `UpdateCharacterState`가 잔여 슬라이드를 피격 경직(Stun)으로 잘못 표시했다.

- 돌진 지속: `selfMoveSpeed / selfMoveDeceleration` = 10 / 20 = **0.5초**
- 공격 클립: Attack 1·2 약 0.27초, Attack 3 약 0.4초 (15fps)
- → 슬라이드가 공격보다 0.1~0.23초 더 길어 매번 발생

리팩터링 이전 커밋에도 동일하게 있던 **원래 버그**다 (`git show HEAD` 확인).

고친 방법: `MovementCore.StopGroundSlide()`를 추가하고, `AdvanceComboOrEnd`에서
자기 돌진이었을 때만(`selfImpulseActive`) 남은 슬라이드를 같이 끊는다.
"돌진은 그 공격의 일부"라는 의미론에 맞추고, 돌진 거리가 클립 길이로 예측 가능해진다.

> 이 버그는 2번(상태 클래스화)이 겨냥한 전형적인 상태 누수다.
> 상태별 `Exit()`가 생기면 이런 종류는 구조적으로 안 생긴다.

**추가 구현 — 공격 캔슬 (X 콤보 중 Z 입력)**

`comboInputBuffered`가 `bool`이라 "다음으로 이어가고 싶다"만 기록하고 "무엇으로"는 버렸다.
그래서 X 콤보 도중 Z를 눌러도 `CurrentAttack.nextAttack`, 즉 X 콤보의 다음 단계가 나갔다.
이것도 리팩터링 이전부터 있던 동작이다.

바꾼 규칙 — 공격 중 입력이 들어오면 세 갈래로 나뉜다:

| 상황 | 처리 |
|---|---|
| 공격 중이 아님 | `startData`로 콤보 새로 시작 |
| **다른** 공격 요청 (X 도중 Z) | 그 공격이 캔슬 권한을 가졌고 타격 프레임을 지났으면 **즉시 캔슬** |
| **같은** 공격 요청 (X 도중 X) | 기존대로 버퍼링 → 클립 끝에서 다음 단계 |

캔슬은 **모든 공격에 주는 권한이 아니라 특정 공격만 갖는 특권**이다.
`AttackData.canCancelOtherAttacks`(기본 `false`)를 켠 공격만 다른 공격을 끊고 들어갈 수 있다.
→ Z(특수)는 X(일반) 콤보 도중 발동, X는 Z 도중 발동 불가.

통과해야 하는 조건 두 가지:

1. **들어오는 공격의 `canCancelOtherAttacks`가 켜져 있을 것**
   기존 에셋은 전부 `false`로 들어가므로, 캔슬을 주고 싶은 공격에만 인스펙터에서 체크한다.
2. **상대 공격이 타격 프레임을 지났을 것** (`hasFiredHitFrame`)
   타격 전 캔슬을 허용하면 계속 갈아타며 공격이 한 번도 안 맞는 무한 취소가 가능해진다.
   → **캔슬 윈도우 = 타격 프레임 ~ 클립 끝.** 시작점 조절용 필드를 따로 안 만든 이유는,
   클립에 이미 심어둔 Animation Event 위치가 곧 캔슬 시작점이기 때문이다
   (윈도우를 넓히려면 그 이벤트를 앞으로 옮기면 된다).

- 같은 공격인지 판별: `currentComboStarter`에 이번 콤보를 시작한 데이터를 기록.
  시작 공격이 하나뿐인 적은 항상 같은 값이라 캔슬 경로를 타지 않는다.
- 캔슬 시 이전 공격의 잔여 Impulse 슬라이드를 끊고 콤보 예약도 지운다(`CancelIntoAttack`).

### [ ] 2. 상태를 진짜 상태머신으로 (불리언 플래그 제거)
**문제**
`isJumpWindingUp` / `isLandRecovering` / `isJumpAirborne` / `isKnockdownLanded` / `isGettingUp` / `selfImpulseActive`
+ `MovementCore`의 `IsGrounded` / `IsGroundSliding` / `IsKnockedBackAirborne`.

이 플래그들이 `PlayerController`에서 42회, `EnemyController`에서 45회 참조된다.
`CharacterStateMachine`을 만들어놓고 판정은 플래그 조합으로 하고 `SetState`는 매 프레임 결과를 받아적기만 한다.
→ 상태머신이 아니라 **상태 표시등**. 전이 규칙(어디서 어디로 갈 수 있는지)을 아무도 소유하지 않는다.

**증거**
`PlayerController.OnHit`에서 플래그 5개를 손으로 하나씩 끄고 있고, 주석에 "여기서 끄지 않으면 플래그가 켜진 채 남아 이동이 영구히 잠긴다"고 적혀 있다. 전형적인 상태 누수.

**영향**
상태를 하나 추가할 때마다(사망, 가드 등) 이 수동 정리 코드가 두 파일에서 같이 늘어난다.

**방향**
- 상태별 클래스가 진입/이탈/입력 허용 규칙을 소유하게 한다.
- 그러면 `OnHit`은 "Stun으로 전환"만 하면 되고, 이전 상태 정리는 `Exit()`에서 자동 처리된다.

**영향**

**방향**
2번을 처리하면 상태 클래스로 자연히 흡수된다. **2번과 묶어서 처리할 것.**

### [ ] 4. Animation Event 의존에 안전장치 추가
**문제**
캐릭터의 조작 가능 여부가 클립에 심어둔 Animation Event 호출에 걸려 있다.
`OnJumpLaunchFrame` / `OnJumpLandEndFrame` / `OnKnockdownGetUpEndFrame` 중 하나라도 클립에서 빠지거나 클립이 도중 교체되면 **캐릭터가 영구 잠금**된다. 폴백이 없다.

같은 맥락으로 `AttackDuration = attackClip.length`가 게임플레이 타이밍의 유일한 출처다.
- 애니메이터가 클립 길이를 바꾸면 밸런스가 같이 흔들린다.
- `CrossFade`의 `transitionDuration`(0.1초)만큼 클립은 늦게 시작하는데 타이머는 즉시 시작해서 미세하게 어긋난다.

**방향**
- 이벤트가 안 오는 경우를 대비한 타임아웃 폴백.
- 타이밍 값을 데이터(AttackData)에서 명시적으로 잡을지, 클립 길이를 계속 쓸지 결정.

## 유지할 것 (건드리지 말 것)
리팩터링 중에 아래 판단들은 그대로 보존한다.

- **코어 로직의 MonoBehaviour 분리** — 이 프로젝트에서 가장 잘한 결정.
- **Intent 패턴** (`IEnemyBrain.Think()` → `EnemyIntent` → 컨트롤러 실행) — 입력 소스 추상화가 제대로 됐다.
- **`AttackData` 다형성** (`AllowsPlayerMovement` / `MoveSpeedMultiplier` / `ApplySelfMovement`) — 컨트롤러에 공격 종류 분기가 하나도 없다.
- **`HitData`가 지상/공중 넉백을 둘 다 싣고 피격자가 고르는 방식** — 역방향 의존을 피한 좋은 설계.
- **입력 시점과 판정 시점의 분리** (`TryStartAttack` / `PerformHitScan`) — 액션게임의 필수 구조.
- **애니메이션의 단방향 의존** (`CharacterAnimatorBridge`가 상태를 구독) — 로직이 애니메이션 없이도 돈다.
- **주석 품질** — "왜 이렇게 했는지"와 실제 겪은 버그 기록. 리팩터링 시 해당 맥락을 새 코드로 옮겨 적을 것.
