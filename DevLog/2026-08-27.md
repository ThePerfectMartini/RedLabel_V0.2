## 🟢 먼저 — 15분짜리 정리 (리스크 0)

### [ ] E. 죽은 API 제거
`CharacterControllerBase`가 Brain을 위해 공개했지만 아무도 안 쓰는 것들:

| 멤버 | 외부 사용처 |
|---|---|
| `CanAct` | **0** |
| `IsGrounded` | **0** |
| `CurrentState` | 사실상 0 (디버그 표시는 `StateMachine.CurrentState`를 직접 읽음) |

`ChasePlayerBrain`이 실제로 쓰는 건 `Position` / `IsAttacking` / `SetFacing` 셋뿐이다.
지우거나, 남긴다면 왜 남기는지 주석으로 근거를 달 것.

### [ ] F. `Update()`를 `virtual`에서 닫기
`protected virtual void Update()`인데 **오버라이드하는 파생 클래스가 없다.**

이 메서드는 순서 의존성이 이 프로젝트에서 가장 큰 코드다
(의도 → 가드 → 이동 → Tick → 착지 엣지 감지 → 위치 반영 → 타이머 → 워치독 → 상태 판정).
실수로 오버라이드하고 `base.Update()`를 빠뜨리면 **에러 없이 캐릭터가 통째로 멈춘다.**

확장이 필요하면 훅을 새로 뚫는 게 맞지 Update를 열어둘 이유가 없다.

### [ ] G. 옛 관용구 잔재 한 줄
`CharacterControllerBase.cs`의 `MoveSpeedMultiplier` 계산이 아직 `attackStateTimer > 0f`를 본다.
결과는 같지만(타이머가 0보다 큰 것과 `phase == Attack`은 동치), 2번에서 걷어낸 옛 판정 방식이
한 줄 남은 것이다. `phase == ActionPhase.Attack`으로 통일.

### [ ] H. 매직 스트링 제거
`AttackData.HasHitFrameEvent()`가 `"OnAttackHitFrame"` 문자열을 직접 비교한다.
이 이름은 `IAttackEventListener`가 노출하는 메서드 이름과 반드시 같아야 하므로
`nameof(IAttackEventListener.OnAttackHitFrame)`로 묶으면 한쪽만 바뀌는 사고를 막을 수 있다.

## 🟡 그다음

### [ ] D. 죽음이 phase가 아니다
**문제**
`OnDeath()` 훅은 있지만 `ActionPhase.Dead`가 없다. 그래서 체력이 0이 된 캐릭터도 여전히:

- `UpdateIntent()`가 불린다 (플레이어는 입력을 받고, 적은 Brain이 계속 생각한다)

- 또 맞을 수 있다

적은 `OnDeath`에서 즉시 `Destroy`하니까 우연히 안 드러날 뿐이다.
**플레이어 사망을 구현하는 순간 바로 터진다.**

**성격 변화**

**구조적으로 자리가 비어 있는 것**이 됐다. 자리가 명확해졌으니 채우기도 쉽다.

**방향**
- `ActionPhase.Dead` 추가, `Update` 맨 앞에서 조기 반환
- `OnHit`도 이미 죽었으면 무시
- 사망 연출(클립 재생 후 제거)은 `Landed`/`GetUp`과 같은 Animation Event 패턴을 그대로 쓰면 되고,

## 🟠 핵심 — 다음 액션 추가 전에 결정할 것

### [ ] B. phase 전이 규칙을 순수 클래스로 (+ A 동시 해결)
**문제**
이 프로젝트에서 제일 잘한 판단이 **코어를 MonoBehaviour에서 떼어낸 것**이었다.
그런데 2번에서 만든 `ActionPhase` 전이 규칙 — 진입 조건, 이탈 정리, 워치독, 캔슬 윈도우 —
은 **MonoBehaviour 안에 들어갔다.**

```
MovementCore       순수 C#        → 테스트 가능 (안 하고 있을 뿐)
CombatCore         순수 C#        → 테스트 가능
ActionPhase 전이    MonoBehaviour  → PlayMode 없이는 못 건드림
```

원래 원칙이 새 코드에 적용되지 않았다. 그리고 **버그가 가장 많이 나온 영역이 정확히 여기다**
(Impulse Stun 오표시, 피격 시 이동 영구 잠김).

**같이 풀리는 문제 (A) — `CharacterControllerBase`가 God object로 가고 있다**

678줄에 책임 10개:
> 직렬화·초기화 · Intent 분배 · 이동 잠금 판정 · 방향 · 공격/콤보/캔슬 · 점프 ·
> 다운/기상 · phase 전이 + 워치독 · 상태 판정 · 피격/사망

"몸"이라는 개념 하나로 묶여 있어서 **지금은 정당하다.** 응집도가 낮은 게 아니라 담당 범위가 넓은 것.
문제는 다음 기능이 들어올 자리다 — 가드·회피·잡기 중 하나만 추가돼도
phase가 늘고 판정·무적프레임·상호작용이 전부 이 파일에 붙는다. 그때 선을 넘는다.

**방향**
- phase 전이를 순수 클래스(`ActionPhaseMachine` 등)로 분리. `Time.deltaTime`을 파라미터로 받으면
  Unity 의존이 전혀 없다
- 쪼갠다면 또 하나의 자연스러운 경계는 공격/콤보 묶음
  (`TryStartCombo` / `StartAttack` / `AdvanceComboOrEnd` / `CleanUpAttack` / 캔슬 규칙, 약 150줄)
- **지금 당장 쪼갤 필요는 없다.** 다음 액션을 추가할 때가 분기점이라는 것만 알고 있으면 된다

### [ ] C. 상태 개념 두 개의 중복 정리
**현황 — 분리 자체는 좋다**

| | 역할 |
|---|---|
| `ActionPhase` | 논리 상태. 전이를 소유하고 게임 규칙을 구동 |
| `CharacterState` | 표현 상태. 매 프레임 재계산, 애니메이션만 구동 |

실제로 `CharacterState`의 소비자는 딱 둘 — `CharacterAnimatorBridge`와 디버그 표시.
순수하게 프레젠테이션 개념으로 잘 정착했다.

**문제는 중복**
`ActionPhase` 6개 중 5개가 동명의 `CharacterState`로 1:1 매핑된다.

```
JumpStart→JumpStart   JumpLand→JumpLand   Attack→Attack
Landed→Landed         GetUp→GetUp         None→(Idle/Move/InAir/Stun/Airborne)
```

즉 `UpdateCharacterState`의 10단 `else if` 사다리는 실질적으로 이 세 줄이다:

```
물리가 Airborne/Stun을 주장하면 그것
아니면 phase != None이면 같은 이름
아니면 물리로 InAir/Move/Idle
```

**영향**
나중에 phase를 추가할 때 사다리도 같이 고쳐야 하는데, **그 연결이 코드에 안 드러나 있다.**
D(사망)를 하면서 바로 겪게 될 문제다.

## 유지할 것 (건드리지 말 것)
1~4번에서 자리잡은 판단들. 이후 작업에서 보존한다.

- **코어의 MonoBehaviour 분리** — 이 프로젝트 최고의 결정. B는 이 원칙을 새 코드에도 적용하자는 것
- **Intent 통일** (`CharacterIntent` → 훅 5개) — 조종 주체와 몸의 분리
- **배타적 상태는 enum으로** (`ActionPhase` / `AirborneOrigin`) — 무효 조합을 표현 불가능하게
- **이탈 정리는 한 곳에서** (`SetPhase` → `CleanUpAttack`)
- **`AttackData` 다형성** + `canCancelOtherAttacks` — 컨트롤러에 공격 종류 분기가 없다
- **`HitData`가 지상/공중 넉백을 둘 다 싣고 피격자가 고르는 방식**
- **입력 시점과 판정 시점의 분리** (`TryStartAttack` / `PerformHitScan`)
- **워치독과 에셋 검증** — 실패를 조용히 두지 않고 원인까지 찍어주는 방식
- **주석 품질** — "왜"와 실제 겪은 버그 기록. 코드를 옮길 때 맥락도 같이 옮길 것
